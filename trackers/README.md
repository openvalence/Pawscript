# pawtrack: Pawscript tracker sidecar

You give it a video, a time range and a box or points. It gives back a position signal and funscript points.
It runs as one process per request: one JSON request on stdin, JSON Lines events on stdout.
The contract with the app is in [PROTOCOL.md](PROTOCOL.md).

## Run

```powershell
# from the Pawscript root (uv fetches Python 3.12 and the deps on first run)
'{"cmd":"list"}' | uv run --project trackers pawtrack
'{"cmd":"scenes","video":"C:/clips/a.mp4","params":{}}' | uv run --project trackers pawtrack
'{"cmd":"track","video":"C:/clips/a.mp4","tracker":"lk_box","start_ms":0,"end_ms":10000,"roi":{"kind":"box","x":0.46,"y":0.43,"w":0.08,"h":0.14},"params":{"axis":"auto"}}' | uv run --project trackers pawtrack

'{"cmd":"loop","video":"C:/clips/a.mp4","start_ms":0,"end_ms":10000,"params":{}}' | uv run --project trackers pawtrack

# score any script against a reference (no video): F1 / precision / recall, fixed-sign F1, timing, r_pos ...
'{"cmd":"score","candidate":[{"at":0,"pos":0},{"at":500,"pos":100}],"reference":[{"at":20,"pos":0},{"at":480,"pos":90}],"start_ms":0,"end_ms":1000}' | uv run --project trackers pawtrack

# tests (synthetic clips: bobbing blob with a cut, a VFR variant, a perfect loop on twos, a rod sliding under an occluder)
uv run --project trackers pytest trackers/tests                # GPU tests skip themselves without the sam2 extra / CUDA
uv run --project trackers pytest trackers/tests -m "not gpu"   # never run them
uv run --project trackers python trackers/tests/make_video.py   # writes trackers/tests/synthetic.mp4 for manual runs
```

### ML extras (SAM 2.1 mask tracker, shot tagger)

```powershell
uv sync --project trackers --extra sam2 --extra describe   # either extra alone works too
```

This installs torch 2.12.1 with CUDA 13.0 from the PyTorch index (Windows/Linux). It needs an NVIDIA driver >= 580 and a GPU from GTX 16xx / RTX 20xx to RTX 50xx (sm_75 to sm_120; GTX 9xx / 10xx and Titan V are not covered by any sm_120 build). Both extras share this one torch. `sam-2` is built from the pinned facebookresearch/sam2 commit with `SAM2_BUILD_CUDA=0`, so no nvcc or MSVC is needed. Its optional CUDA hole-filling op is skipped, and we don't need it. The base install and `list` never import torch. After installing, plain `uv run` keeps the extras. `uv sync` without the `--extra` flags removes them.

Checkpoints download on first use and print their URL and licence to stderr. SAM 2.1 goes to `trackers/.cache/sam2/` (tiny 156 MB, small 184 MB, base_plus 323 MB, large 898 MB). Hydra goes to `trackers/.models/hydra/` (~1.1 GB). Both dirs are gitignored.

What it does:
- **Timestamps** are container PTS, rebased so the file starts at 0, like mpv and `<video>.currentTime`. They are never computed as frame index / fps, so VFR files work.
- **Cuts.** `track` runs the cut detector over the range first (the same one as `scenes`). At a cut, that frame's `value` is `null`, the tracker restarts there from the original ROI, and each scene is normalized and turned into points on its own. Turn this off with `"cut_enabled": false`, or pass the cut times yourself with the request's `cuts` (`[]` = one scene; PROTOCOL v3.1). **Soft cuts** (PROTOCOL v4.9): a cut sent as `{"t_ms", "kind": "soft"}` marks a change where the action goes on (a camera split, a `continues` scene, a pan / zoom / orbit starting or stopping inside a scene; the app sends these, and `track` without `cuts` adds the detector's camera splits itself). The run does not restart there: every point keeps its index, group, part and pinned group, and the result's `scenes` are the hard cuts only (one group id space each). The points trackers run a re-seed pass on the first model step at or after the cut: hidden and off-frame points are retired at once (not after `retire_ms`), voids are filled over the hull and the ROI box (the box re-applied where the frame now shows it), and a pinned group (`sem_*`) whose tagger region is back on that frame but has fewer than half its points visible is refilled there under its old id (`scenes[].groups.sem_<name>.refilled`). The count stays the cap (retire before admit: off-frame first, then longest hidden; visible points are never retired; voids beyond the free slots wait for the next check); `max_points` opts in to growth. Each soft-cut segment is also normalized on its own (its own robust range; a segment under 1.5 s joins the one before; the ranges cross-fade over 0.5 s, so there is no step). **Camera trend** (`pipe_cam_detrend`, default on): in a piece where the camera travels (the detector says pan / zoom / orbit / handheld, or the motion groups' camera path moves the primary by > 1.5x the stroke) and the strokes are drowned (stroke amplitude < half the piece's range) and periodic (velocity autocorrelation >= 0.3), the trend is removed before normalizing: the groups' camera path regressed onto the primary when `cam_conf` >= 0.3, then a median-then-mean over one stroke period if a trend is left; the removal is relative to the piece's start and carried on, so nothing steps. Per piece the `primary` note and `scenes[].segments` say kind, method, trend removed (px) and stroke share before / after. A panning stroke whose pan used to set the range (strokes < 0.2 of it, few or no turns) keeps its strokes (share 0.15 -> 0.91 median on the 26 drowned periodic gold pieces); F1 on the gold pan clips 0.478 / 0.448 -> 0.508 / 0.483 (free / fixed sign), all 199 scenes 0.507 / 0.474 -> 0.512 / 0.483 (`experiments/softcuts/RESULTS.md`).
- **Fades, blanks, dissolves, flashes, stills** (`pawtrack/scenes.py`, CPU, the same 160 px pass, +0.3 ms/frame over the hard-cut test: 0.17 -> 0.48 ms/frame on the gold clips). A hard cut is a mean HSV jump >= 3x the recent window's largest (twos-safe) and >= 15, or (`cut_repeat`, paw-fc0r) a jump >= 15 whose frame has no near twin in the last 1.5 s while the frames before it do (a cut between two fast loops: 5x the window's largest such novelty; on the owner's 8 corrected projects recall 96 -> 101 of 110 cuts, 1 extra, `experiments/cuts/RESULTS.md`; +0.14 ms/frame). On top: a **blank** (luma mean < 16 or > 240, luma std < 10, >= 150 ms) is its own scene (`kind: "blank"`) together with the monotone **fade** ramps into and out of it (>= 200 ms, >= 20 luma levels toward the blank, the same picture frame to frame; the walk stops where luma has been flat for 250 ms), so the scene before ends where its fade-out starts and the next begins where its fade-in ends. A **dissolve** (>= 300 ms of small steps whose ends differ by a cut-sized jump, >= 2x the change over the same span just before, and whose inner frames are blends of the ends: correlation of (x - a) with (c - a) >= 0.8 at 1/4, 1/2, 3/4 on 32 px BGR frames, weights increasing) gets one cut where the blend passes 0.5. A **flash** (a cut whose picture returns within 80 ms) is no cut. A **still** (>= 2 s of frames with < 1 % of pixels moving > 4 grey levels) marks the scene `kind: "still"` when it fills it and is split off when it opens or closes one; a pose held inside a scene is not a cut. Each scene says how it starts and ends: `transition {in, out, in_ms?, out_ms?}` (`cut` / `fade` / `dissolve`). Gold clips (18 videos, 88k frames, no reference cut lists): 222 hard cuts before, 305 boundaries after; 193 unchanged, 28 moved (a cut that landed at a fade's end now sits at its start, or a fade-out became blank + fade), 86 added (47 blanks, 31 dissolves, still splits), 1 removed (a cut one frame before the end); 51 fades (median 0.67 s), 35 stills, no flashes. 21 of the 47 blanks have at most one scripted action inside: the scripters hold there. Synthetic cases (each also on twos): `tests/test_scenes.py`.
- **Camera moves** (`pawtrack/camera.py`, CPU, no ML, ~0.7 ms/frame at the cut detector's 160 px grey). Per frame pair: Shi-Tomasi corners + pyramidal LK + a RANSAC partial-affine fit give the global translation and scale (inlier share = confidence), plus the median motion of the border ring and of the centre; with too few corners phase correlation stands in. Held frames (twos / threes, static shots) are skipped and the next drawing's motion is spread over them. Over a 1 s window, net motion against oscillation sorts the camera into two natures: **progressive** (net displacement: `pan` incl. tilts with the camera's direction, `zoom` in / out, `orbit` = turntable: the border streams past while the centre stays put, plus `handheld` = aperiodic shake) and **reciprocal** (no net motion, a periodic bob: the camera rides the stroke, its path is a stroke signal); else `static`. Hysteresis (exit at 0.6x) and 400 ms minimum segments; a scene shorter than 1 s is static. `scenes` returns `camera` segments per scene and, with `cut_camera` (default on), splits a scene where the camera turns progressive or steady again (`cut_min_scene_ms` respected; static <-> reciprocal never splits); the later pieces carry `continues: true, split: "camera"` (the same shot, one continuing action, no cutaway). `track` reports `scenes[].camera` but never splits a run at a camera move: the app sends camera splits and the camera moves inside a scene as soft cuts (v4.9, above). Gold set (244 cached CoTracker3 scenes, `eval/camera_eval.py`, the same classifier on the grids' `cam`): 0.89 frame agreement moving vs not, 0.86 on the scene's dominant kind; scenes called reciprocal have a camera path that correlates with the reference script (median |r| 0.58 vs 0.22 elsewhere). The tracker's `cam` has no reference in big pans (`cam_conf` low, points leave the frame), so most pan disagreements are on its side.
- **Turning stroke axis** (`pipeline.rolling_axes`, used by `groups.pair_dist` when no `axis` is given). The principal axis is fitted per 4 s window (hop 1 s, sign kept continuous) and used frame by frame when the clear windows' axes span more than 20 deg over the run (a turntable turns the stroke in the image); otherwise the output is byte-identical to the scene-wide axis. A clear window needs >= 1/4 of the windows' p90 variance (`ROLL_Q`; was the median: with the sticky group ids a pair run holds sync stretches with no relative motion, whose noise windows turned the axis). Gold set (`experiments/groups/probe.py`, 245 scenes, rolling on 65): `pair_proj` F1 0.548 -> 0.559 (fixed sign 0.470 -> 0.493). The same rolling axis in `project_auto` (`proj`, `g*_proj`) lost (largest body 0.555 -> 0.518, with the overall sign aligned), so those stay scene-wide; the gold set has a single short orbit scene, so neither number is a turntable measurement.
- **Live values.** A `frame.value` is normalized over what has been seen so far in the current scene. The final `samples` are normalized over the whole scene.
- **Params.** Every tracker accepts its own params, the `pipe_*` pipeline params, the `cut_*` cut params and `held_retime` / `loop_fold` / `loop_min_confidence`. `list` shows them all. Unknown keys are an error.
- **Held frames and loops** (`pawtrack/loops.py`, no ML). This works on 64 px grey thumbnails. Frames that repeat the previous one are detected (99th percentile of the pixel difference against a noise floor), which gives the dominant step (twos, threes). The period comes from the RMS difference between frame i and i+lag over all i (one Gram matrix): the first valley of that lag curve at least 0.8x as prominent as the most prominent one. It is `exact` when the difference there drops to codec-noise level (confirmed by its multiples), `periodic` when the valley is clear but the cycles differ. (The old rule, "smallest lag near the floor", returned lag 2 on almost all real footage because the curve just rises.) On the reference set: 2 exact loops and 27 periodic scenes out of 80. Analysis takes about 10 ms per 250 frames, and decoding at 64 px wide runs at about 8-9k fps on 640x360 mp4v. `held_retime` keeps one sample per drawing and interpolates. `loop_fold` takes the median of every phase over all cycles and tiles it back; `auto` does it for exact loops only. Folding assumes a constant frame rate and a whole-frame period inside the range.
- **Points** (`pawtrack/pipeline.py`, params in PROTOCOL.md). Position convention: pos 0 = deepest, 100 = out. Turning points of a smoothed signal normalized by a rolling 3 s robust range (a global min-max let drift or one big move squash every small stroke: on fast scenes it cut stroke recall from 0.63 to 0.35), extremes only, turn times between frames. A near-still window is not stretched (`pipe_norm_floor`: the range never counts narrower than 0.75 x the scene's median stroke). Then over the whole range an activity gate that only flags: low thumbnail motion at the range ends is `idle`, inside it is `still`; the points stay as tracked. `spans` from the UI, the tagger or a story timeline override it, and only an `idle` (hold) or `carry` (the neighbouring rhythm continues) label changes points. Evaluation numbers: `trackers/eval/out/changes.json`.
- **One big knot** (a single slow insertion over a few seconds, then held deep). The points pipeline loses it (no turning points, the rolling range flattens the trend). A knot-in hold mode for the sidecar (an isotonic fit of the raw primary inside the knotting tag's span) was measured on the 12 big knots in the gold scripts (10 of 245 scenes) and **not shipped**: push RMS 41 -> 30-38 pos, but a plain push over the span with no signal at all scores 21-26, at every span padding (`experiments/knotin/RESULTS.md`). The tracker barely sees the push on 3 of 12 and runs the other way on 2. The app's Knotting effect in mode **One knot** draws the push, pop, settle and tie over the span instead (`src/lib/fx.js`).
- **Direction.** Motion alone cannot tell deep from out. No cheap heuristic tested (velocity skew, position skew, motion energy at the extremes: the stroke end where the picture moves least as "out" was right in 61% of scripted scenes for the ROI-free PCA / flow-ROI baselines but only 46% for the flow baseline) was clearly better than chance across signals, so a scene keeps the tracker's own orientation (or a confident shaft's) and the user flips a scene (`pipe_invert`, reported in `scenes[].sign`).
- **Raw amplitude.** Every tracker fills a `raw_px` channel: its primary signal in frame pixels before the per-scene normalization. For `lk_box` / `template` that is the displacement on the axis (`auto`: the distance from the start position, unsigned). For `lk_two_point` it is the distance. For `sam2_mask` it is the centroid coordinate for the centroid primaries, else the visible length `axis_len`. For the point trackers it is `proj` (or `dist01`) unscaled. Normalization turns any motion into a full 0..100 stroke, so when a scene's raw peak-to-peak stays under 4 px the tracker logs `pawtrack: info: <tracker> raw_px peak-to-peak ...` to stderr. The plug-in contract has no info event yet, so the UI should also check `raw_px` itself.
- **GPU memory.** `pawtrack/vram.py` caps the process's CUDA memory at (the models it keeps loaded) + (this job's need: describe 3 GB, sam2_mask max(3, 2 + 0.004 x chunk_frames) GB, the trackers' measured needs below, the tagger 1.8 GB / SAM 0.6 GB beside them), unloading the least recently used models the job does not need when that would pass the budget (the card's free memory, `PAWTRACK_VRAM_GB`, or `PAWSCRIPT_GPU_FRACTION` from `trackers/gpu_lock.py`, which wins), so nothing spills into system memory; an out-of-memory error anyway unloads the rest and retries once, then says in words what was loaded and needed (PROTOCOL.md § GPU memory).
- **CPU threads.** The points trackers' motion-groups pass (`groups.group_tracks`, CPU only) runs its independent windows and fits on a thread pool of all logical cores (`PAWTRACK_THREADS`, else `OMP_NUM_THREADS`, overrides; the owner waits on it, paw-v0oe) with numpy's BLAS on one thread meanwhile and the previous BLAS setting restored after, so inference and the rest of the sidecar are untouched. Its output does not depend on the thread count and is bit-identical to the single-threaded code before (`tests/test_groups_speed.py`). Synthetic 3000 frames x 2458 points, 6 pinned groups: 96 s -> 56 s on 1 thread, 94 s -> 21 s on 4.

## SAM 2.1 mask tracker (`sam2_mask`)

The ROI is a box or positive clicks on the scene's first frame. The video predictor propagates the mask, and channels are measured on it (units in PROTOCOL.md). `len_over_width` is the default primary. It is the insertion-depth candidate: the visible shaft gets shorter while its width stays the same, so shorter = deeper = lower pos (pos 0 = deepest).

- **No frames on disk.** Frames are resized to 1024² and handed to SAM 2 from memory. This patches `sam2.sam2_video_predictor.load_video_frames`, which ties it to the pinned commit.
- **Chunks** (`chunk_frames`, default 150). Each chunk is a fresh predictor state holding [scene's first frame + the original prompt, the previous chunk's last frame + its mask, new frames]. The object keeps its original anchor and stays continuous, and memory is bounded by the chunk, not by the range. Frames are held on the GPU as uint8. Measured cost: about 1.0 GiB plus about 3.9 MB per chunk frame (small model, 1080p): 150 → 1.2 GiB, 600 → 2.8 GiB, 1800 → 7.2 GiB peak allocated. The ceiling is `chunk_frames` 2000, about 8 GiB. Chunking cost no measurable fps. Live `frame` events arrive in bursts of one chunk.
- **Which end is the base** (for `bulge`). Without an anchor this is ambiguous. Param `bulge_base`: `auto` takes the axis end that has moved least so far in the scene. The ends are tracked frame to frame, so the base is also the more stable end, typically the root. It is undecided on frame 1 and can flip early in a scene if both ends move similarly. `top`/`bottom`/`left`/`right` force it. `bulge` is only a measurement. No knot events are emitted yet. Its reference width is the shaft width, the 25th percentile of the slice widths. The old reference, the median of the middle third, was the knot itself whenever the visible part was short, so the knot never showed while it was passing (synthetic knot clip, `tests/test_sam2.py::test_sam2_knot`). The ROI box is only the first-frame prompt: the propagated mask is never intersected with it, and no connected component is picked for the stats.
- **Speed and VRAM** (RTX 4090, torch 2.12.1+cu126, bf16 autocast, 1080p input, one object, chunk 150, frames/s after the first frame):

| model | fps | peak VRAM allocated / reserved | model load + first frame (warm cache) |
|---|---|---|---|
| tiny | 33-35 | 1.10 / 1.28 GiB | 1.4 s |
| small (default) | 33-34 | 1.13 / 1.31 GiB | 1.3 s |
| base_plus | 29 | 1.28 / 1.51 GiB | 1.7 s |
| large | 18 | 1.88 / 2.21 GiB | 2.5 s |

tiny and small run at the same speed because per-frame overhead dominates (1080p decode, resize, Python, GPU sync, mask measurement), so small is the default. Every request starts a new process, so it reloads the model.

## Point trackers (`cotracker_points`, `tapnext_points`)

```powershell
uv sync --project trackers --inexact --extra sam2 --extra describe --extra tapnext
```

**CoTracker3 is optional, not included** (paw-vdr4, paw-uekm): its package, its checkpoints and `pawtrack/trackers/cotracker_points.py` are in no build and not in the public source (CC-BY-NC 4.0). `list` names `cotracker_points` only where a developer installed all three by hand (PROTOCOL v4.57); everywhere below, the shipped tracker is `tapnext_points`, which takes the same params.

Long-range point trackers: TAPNext++ (Google DeepMind, Apache-2.0), and CoTracker3 (Meta, CC-BY-NC, optional, not included). ROI `points` (clicks, tracked as given) or `box` (seeded with `box_seed` grid / line / motion and `box_points`, plus the pinned groups of `sem_groups`). Each point gets a position and a visibility on every frame. Channels:

**Recommended workflow: click 2-4 points on the moving part, then draw the stroke axis.** Use `"axis":"custom"` with `axis_x0, axis_y0` at the OUT end and `axis_x1, axis_y1` at the IN end of the thrust (normalized frame coords). The default primary `proj` then moves toward pos 0 when the part moves toward (x1, y1), so a single click pair gives the right direction. With `axis:"auto"` the stroke axis is the principal axis of the points' motion, which gives the right timing but an arbitrary direction (up / right = higher, like `centroid_auto`).

| channel | unit |
|---|---|
| `proj` | the points' centroid projected on the stroke axis (`axis` auto / vertical / horizontal / custom), 0..1 over the scene. The centroid is the seed centroid plus the mean displacement of the visible points, so it does not jump when some points are hidden. Gaps with no visible point up to `gap_ms` (default 1000) are interpolated, with confidence x 0.1. **Default primary** (`primary: auto`) for one click, a box, and several clicks on ONE body (a box whose pinned hips are found: `sem_hips_proj`, below) |
| `proj_cam` | `proj` with the camera removed: the same centroid minus `cam_x`/`cam_y` (the motion groups' camera), through the same pipeline (axis, sign rule, gap bridging, 0..1 per scene; with `axis: auto` its axis is fitted on its own track). Use it when `proj` rides a slow carrier (pan, drift). Grey it out when `cam_conf` is low: with no camera reference it equals `proj`. Valid `primary` (`primary_used` 2; `raw_px` then follows it) |
| `raw_px_cam` | `proj_cam` before normalization, frame px |
| `cam_conf` | share of the co-visible points the camera step came from, 0..1 (0 = no reference that frame, `cam` held). Reference: the static group when a moving group is present and the static points move less on screen at stroke frequencies than the moving ones; else the points that barely move on screen at stroke frequencies (high-passed RMS < max(0.0025, 0.25 x p90)); else none. Rule in `pawtrack/groups.py` |
| `primary_used` | what `auto` chose for this scene: 0 = `proj`, 1 = `dist01`, 2 = any other primary (explicit, or auto's `sem_hips_proj`) (the reason is also logged to stderr) |
| note `primary` | not a channel: the scene's decision record in `result.notes` (PROTOCOL v3.2): `chosen`, `rule`, numbers per candidate primary (std / travel in frame heights, valid share, `cam_conf`, group share), `axis`, `sign` (keep / shaft, invert, applied), `camera`, `low_motion`, `cadence_fill`, `held_input` (`primary_record` in `cotracker_points.py`) |
| `vis_frac` | share of the points visible (0..1): fewer visible = more hidden = deeper = lower pos |
| `vis_extent` | share of the seed cloud's long axis (rest frame) that the visible points span, 0..1 |
| `vis_len` | span of the visible points along their own principal axis now, frame heights |
| `dist01` | distance between clicks 0 and 1, frame heights. `auto` picks it only when the clicks span two bodies: std(dist01) >= 0.5 x std(centroid travel on the axis) |
| `centroid_x`, `centroid_y` | the cloud's seed-anchored centroid (seed centroid + mean displacement of the visible points, as `proj`'s: points hiding do not move it), normalized frame coords |
| `p0_x` ... `p3_y` | the first 4 points, normalized frame coords |
| `cam_x`, `cam_y`, `cam_conf` | the group pass (`pawtrack/groups.py`): points bucketed by trajectory correlation into still points and moving groups (sticky ids, parts per body: `pawtrack/motion_model.py`); its camera estimate is the cumulative motion of the still points. The groups themselves are not channels (PROTOCOL v4.60); the overlay `pts` carry the group per point (4th element) and the part (5th). Probe on the gold clips: `experiments/groups/RESULTS.md` |
| `sem_penis_x` ... `sem_hips_area` (`_x`, `_y`, `_n`, `_proj`, `_rel`, `_scale` per group; v4.6; `_area` v4.8) | pinned semantic groups (`sem_groups`, below): penis / balls / hips seeded from the tagger on the seed frame, fixed members for the scene. Centroid of the visible members (camera removed), their share of all points, `_proj` = the centroid through `proj`'s code path (a valid primary), `_rel` = its motion in the frame of the body around it, `_scale` = its own contraction (raw, null with < 3 visible members), `_area` = its part's mask area as a frame share when the outlines are tracked through the scene (opt-in, below; else null; a valid primary). Null when the group was not found or has no visible member |

`primary` also takes `centroid_auto` and `proj_cam`. Because `proj` needs the whole scene (axis, range, auto choice), the tracker buffers a scene and emits its frame events in one burst at the scene's end. `confidence` is CoTracker3's confidence head, or TAPNext++'s coordinate-head sharpness, averaged over the points. The overlay draws visible points as `points` and occluded points as small `boxes`, because the overlay has no per-point flag. TAPNext++ tracks clicks together with support points (a 6x6 frame grid plus a 5x5 patch around each click) that are then dropped, as its VOTS tracker does; without them it loses a lone click under occlusion. CoTracker3 tracks the clicks alone, because any support points made it worse on the synthetic rod.

Modes. `cotracker_points` `mode`:
- `online` (default): 16-frame sliding window, constant memory, results in bursts of 8 frames.
- `offline`: bidirectional inside chunks of `chunk_frames` (default 32). Every chunk starts with the scene's first frame, which carries the queries, so tracks stay anchored. They are not continuous across chunk borders.

`tapnext_points` is recurrent and strictly causal. `model` `256` / `512` picks the input size (and the checkpoint); `auto` (v4.55, default) runs 256 unless the scene's smallest painted part is under 2.7 % of the frame across (its outline's short side in the square model input), then 512 when its checkpoint is there and it fits the VRAM budget; note `model_size` says which and why (experiments/resolution: 512 wins only on small parts, 256 is 3.6x faster). `chunk` (default 8) is frames per forward call, about 2.5x faster than 1. Visibility was identical to per-frame on a test shot, the median position difference was 0.006 px, but a few points diverged (fp16 recurrence). `chunk` 1 is the strict upstream behaviour.

`held_input` (both, default `auto`): animation on twos/threes is tracked on its own clock, only new drawings go to the model and held frames repeat their drawing (PROTOCOL v3.1).

**Re-seeding** (both; params `reseed_every_ms` default 1000, 0 = off; `retire_ms` default 2000; `max_points` default 0 = the initial count). Points are no longer only made on the scene's first frame: every second the tracker looks for voids in its own cloud and seeds them, in the same single pass. The void grid is the box's own seed grid (at most 64 cells, so every first-frame seed starts in its cell), extended over the whole frame; clicks use 8 x 8 over the frame. A void is a cell with no visible tracked point inside the region: the whole frame for a box covering >= 80 % of it, else the convex hull of the currently visible points (a body box keeps up with a body that grows in a zoom or pan, but does not spill onto the background). It fires only when there are more voids than the first-frame layout itself left (line seeds, clicks), and it skips flat cells (grey std < 6 of the cell's central patch, the cells trackers lose first). Each textured void cell gets one point at its centre, most textured first, in the slot of a retired point: hidden for > `retire_ms` or off-frame (off-frame first, then longest hidden; clicks are never retired). **The active point count stays the initial count** (retire before admit), so model cost and VRAM do not change; `max_points` above it opts in to more points (then the state grows until it is full). Nothing is retired unless a new seed takes the slot, and a scene where nothing is re-seeded gives byte-identical output (`tests/test_reseed.py`). Every point keeps its index in the overlay `pts` for the whole scene: a re-seeded point is a new index, `v 0` before its birth, and a retired one stays `v 0` with no `boxes` entry (the shape is unchanged; `pts` is longer than the initial count after re-seeds). The signals do not step when points come or go: a new point is anchored at its birth position minus the cloud's mean displacement on that frame, so it enters carrying that displacement (`anchors()`), and `vis_frac` counts only the alive points. Clicks stay points 0.. (dist01, p0..p3). Info note `reseed` per scene. Offline CoTracker3 does not re-seed (its chunks re-derive from the first frame).

Both models take a new point in their running state: the slot's state is reset in place and its query set to the next frame (`online_reseed`, `refill`: no state copy). CoTracker3 online keeps its points on one axis of the online state, and a query whose frame the model has not reached yet starts empty, so this is how upstream handles late queries anyway. **Seed frame** (both; v4.3). The ROI is laid on one frame per scene and tracked both ways from it: forward to the scene end, and the same buffered frames reversed back to the scene start, merged in time order with the seed frame shared (`merge_passes`). The frame is the one the ROI was drawn on (`roi.t_ms`, for the scene that contains it), else per `seed_frame`: `first` (default; streamed exactly as before, byte-identical) or `auto` = the medoid of the scene's 64 px grey thumbnails, its most typical frame. Both passes re-seed with their own `Reseed`, its clocks fed mirrored time (2 t_S - t) so retire / every-second logic runs forward. A pass's re-seeds are new indices, not alive in the other pass's frames. Anchors are taken on the seed frame (the seeds' own positions there), so `proj`, `vis_frac`, `dist01` and p0..p3 keep their meaning, and held_input picks the drawings once in time order and tracks them both ways. Measured on 26 gold scenes (`experiments/seedframe/RESULTS.md`, CoTracker3 online, whole-frame box, 64 points): on the 12 scenes that do not open on their typical content, coverage goes from 0.67 to 0.89 with medoid (+0.08 on orbit and pan scenes, flat on the controls). `proj` F1 moves within noise (-0.04 openers, +0.06 orbit, -0.02 pan), so `auto` stays opt-in. Texture, most-different-from-first, keyframe and textured-cell picks did no better. Several seed frames per scene (points split between them) were no better and cost 3x, so they are not shipped. The bidirectional run costs the scene once plus one model init, with the same peak VRAM (1.51 GiB). The scene is buffered at the model's input resolution (about 0.6 MB a frame for CoTracker3). **Travel trigger**: between the timed checks, a void check also runs when the visible cloud's median displacement since the last check is at least one void cell and stays so over every lag of 0.5-1 s (a pan or orbit; a reciprocal bob returns within that window and does not trigger it). On the panning gold scenes this added about 16 re-seeds per scene and +0.007 coverage (constant n). It did not fire on the orbit scenes, because their clouds rarely travel a cell within a second. A box covering >= 80 % of the frame re-seeds anywhere, so the strip a pan reveals gets points. A mid-size box re-seeds only inside the hull of its visible points: it keeps up with a subject the camera follows, but a strip of background that pans in stays empty by design. If the subject itself leaves the frame, draw the box again. On a turntable or orbit shot the same rules apply (seed frame, then re-seeding every second and on travel). If a run loses the subject, scrub to a frame where it is fully in view and draw the box there (`roi.t_ms`).

**Pinned groups: outline and pruning** (v4.8). Tracker params `sem_shape` (`cam` = the CAM blob as is, `grabcut`, `sam`) and `sem_track` (bool) pick the outline and the propagation per request; the panel shows them with the box params. Points that land outside the part (background, the other body) do not move with it and pull the group's centroid and `_scale`. Three guards (`partlabel.shape_regions`, `cotracker_points.box_seeds` / `Reseed` / `motion_outliers`): (1) **outline on the seed frame**: GrabCut (`sem_shape: grabcut`, the default (`partlabel.SHAPE`); CPU) at 320 px, 5 iterations, the CAM blob probable foreground, its >= 0.8 x peak core sure foreground, a one-patch ring around it probable background, everything else (and the other regions' cores) sure background, so the outline can trim the blob and grow at most one patch. `sem_shape: sam` (opt-in) prompts the SAM 2.1 tiny image predictor with the CAM peak + 2 hot cells as positives and the other regions' peaks + 2 low-CAM cells off the blob as negatives, keeps the candidate with the best IoU with the blob, and rejects a mask > 3 x the blob (swallowed the body: GrabCut instead) or with < 6 textured pixels (the blob instead). The pinned points are then drawn on the mask's pixels at 256 px, 1 px inside its outline, textured pixels (5 x 5 grey std >= 6) first, at >= half the mean spacing. (2) **motion consistency**: at every re-seed check (`reseed_every_ms`; off with re-seeding off) each pinned group's members over the last 1.5 s (the seed positions count as the first window's first sample) get the group's robust similarity fit (`motion_model.fit`); a member whose RMS residual is > 3 x the members' median (and > 1 px at 384 px), or, while the group moves, whose displacement correlates < 0.3 with the group's (a static member: 0, dropped first), is retired (at most half the judged members per check, >= 5 judged) and re-seeded inside the hull of the group's inliers on textured pixels; the group keeps its 10 % share. (3) **through the scene** (`sem_track`, opt-in; default `partlabel.SEM_TRACK`; propagates the `TRACK_PARTS` parts): the outlines are propagated by the SAM 2 tiny video predictor (512 px, every 2nd frame, masks held between; the scene is buffered); a pinned point counts for its group only while inside its part's mask (`pts` shows it occluded outside), one outside for > `retire_ms` is re-seeded on the current mask, and `sem_<name>_area` carries the mask area. `scenes[].groups.sem_<name>` gains `source` ("grabcut" | "sam" | "cam"), `mask_px` / `blob_px` (pixels at 256 px), `sam_reject`, `pruned`, `tracked`; the `primary` note's `seed` gains `shape_ms` / `track_ms`. **Not yet measured on the gold set** (the GPU lock never admitted the run; synthetic tests only): `experiments/seedmotion/measure_sem.py scan`, then `track <variant> 256` for `before` (PAWROOT = a copy of the pre-outline code), `cam`, `grabcut`, `grabcut+prune`, `sam+prune`, `sam+track`, `sam+track2` (penis + balls only), and `sem_summary.py 256 <variants>` (first-window outlier share, balls `_scale` presence and its correlation with the high-passed script, `sem_hips_proj` F1, `sem_penis_scale` jitter, outline / propagation ms, peak VRAM); `sam_cost.py` gives SAM's load, per-scene ms and VRAM alone. **Motion-weighted seeds** (both; `box_seed: motion`, opt-in; v4.6). The idea is to spend the box's points where things move instead of on a uniform grid. The scene is buffered (as for a seed frame), and a CPU pass of DIS optical flow (ultrafast preset) runs at 256 px wide on frames ~0.1 s apart. Each pair's median flow (the camera) is removed and held drawings are skipped. The mean |flow| makes a motion map. The layout has three parts: a floor of max(16, n / 4) grid cells, one point on each textured cell; one point in every moving cell (energy above the median) of the 8 x 8 void lattice; the rest drawn over a fine sub-lattice in proportion to energy^0.5, capped at its 90th percentile. Flat cells get none, unless the frame is mostly flat (dark or fading), in which case texture is ignored. Re-seeding uses the grid's 8 x 8 lattice with the flat cells as its base, so every textured empty cell gets filled as with the grid. The flow pass costs about 1.2 ms per sampled pair: 250 ms mean and 430 ms max per 30 s scene (DIS fast: 2.2x that, cell maps r = 0.97 apart). ## Cumshot proposals (`cum`)

`{"cmd":"cum","video":..,"start_ms":..,"end_ms":..,"params":{..},"pulses":[ms,..]?}` -> `{spurts: [{t_ms, score, source, strong}], curve: {t, cum}, frames, tagged}` (PROTOCOL v4.7). Proposed spurt times for an orgasm scene: the app shows them as ghost diamonds and the owner places them (never automatic). `pawtrack/cum.py`; needs the `describe` extra and CUDA; in `serve` it runs in the describe child (it imports Hydra).

- **Signals** per decoded frame of the range: the shot tagger (Hydra 3.5, as `describe`, every k-th frame for ~`fps` 12 per second, seqlen 512) gives `tag` = the max probability of the spurt tags (ejaculation, cumshot, cum_spurt, cum_string, cum_from_penis, cum_explosion, cum_splatter, orgasm) and `cam` = the CAM mass of cum / ejaculation / cumshot; every frame gives `fluid` = the share of bright, low-chroma pixels new since the previous frame inside the penis / balls / cum CAM boxes (padded 25 %).
- **Rule** (the shipped one, all thresholds are params): onset strength of `tag` and `cam` = their rise across a centred 250 ms window, of `fluid` = itself; each scaled by max(its p99, 8 x its noise sigma) so a range of noise stays low; fused = the mean of the three; spurts = fused peaks >= 120 ms apart with score >= 0.15 (`strong` >= 0.5). A peak within 100 ms of a caller `pulses` time (the app sends the balls contraction peaks of a tracker run's `sem_balls_scale` when there is one) gets x 1.5.
- **Validation** (`experiments/cum/`: `run_feat.py` features, `evalcum.py` / `table.py` scores; numbers only, no frame viewed): the 14 orgasm spans of `experiments/orgasm` (RESULTS.md). Ground truth = one dip per cycle of the reference script's orgasm pattern (valleys with prominence >= half the span's p5-p95 range, >= 250 ms apart). These scripts are periodic burst patterns (many are copy-pasted 0.67-1.1 s loops), not one marker per cumshot, so the target is weak; "chance P" = the precision of random times (the share of the span within the tolerance of a dip). 14 spans, 247 script dips, 253 s of orgasm in all; precision / recall with one-to-one matching at ±100 / ±200 ms.

## Director service (`pawtrack serve`, frames, motion.*, director.ask)

Shapes: `src/lib/director/README.md` §8; additions in PROTOCOL.md ("Director commands"). Every command also runs one-shot.

```powershell
uv run --project trackers pawtrack serve            # or: <trackers\.venv python> -m pawtrack.cli serve
python trackers/gpu_lock.py --gb 8 <abs trackers\.venv\Scripts\python.exe> -m pawtrack.cli serve   # dev / eval with the GPU
uv run --project trackers pytest trackers/tests/test_serve_session.py trackers/tests/test_motion_stats.py trackers/tests/test_motion_compare.py trackers/tests/test_frames.py
python trackers/gpu_lock.py --gb 8 <abs trackers\.venv python> -m pytest trackers/tests/test_serve_vlm.py -s -m gpu
```

- **One process, models kept.** Jobs run FIFO on a worker thread; `cancel` / `status` / `unload` / `shutdown` are
  answered at once. Cancel is cooperative (the next progress/frame event of the job raises). SAM 2 now keeps its
  predictor per process (`sam2_mask._PRED`), CoTracker/TAPNext keep theirs (`_MODELS`); switching GPU tracker drops
  the previous one.
- **Hydra/sam2 name clash.** The Hydra tagger's code is a package called `hydra`, sam2 imports hydra-core's `hydra`;
  only one can be imported per interpreter. `describe` therefore runs in a resident child `pawtrack serve --role
  describe` (same interpreter, started on first use, 3 GB cap). Everything else runs in the main process.
- **VLM.** `director.ask` with `qwen3.5-2b|4b` loads in-process if `transformers` imports; otherwise it starts
  `pawtrack/vlm_worker.py` (= `serve --role vlm`) under `PAWSCRIPT_VLM_PYTHON`, default
  `trackers/experiments/vlm/.venv/Scripts/python.exe` (torch 2.12.1+cu126, transformers 5.22.2, bitsandbytes 0.50.2:
  the same torch as here). No `vlm` extra was added to `pyproject.toml`: the worker route needs no change to the lock.
  Prompt = the stage director's system prompt + question + "Answer with exactly one word from: …"; the first token of
  each choice is counted with its `Yes` / ` yes` variants (as `experiments/stage`), choices must differ in their
  first token. `bonsai-*` start the owner's llama-server (`PAWSCRIPT_LLAMA_SERVER`, default the LM Studio PrismML
  build) on a private port; it is not VRAM-cappable (~7.5-8.8 GB measured by `experiments/stage/bench_bonsai.py`).
  One-shot unloads after the request; serve keeps the model until `unload`, 120 s idle, or eviction.
- **VRAM.** `PAWSCRIPT_GPU_FRACTION` is read once: budget = fraction x card. Caps: tracker 4.3 GB (in-process; its
  fraction is set to what the children leave), describe child 3 GB, Qwen 2B bf16 6 GB / nf4 3.5 GB, 4B bf16 10.5 GB /
  nf4 5 GB (children get their own fraction, not the parent's). A job that would overflow the budget evicts the VLM,
  then the tracker, then describe. `status.resident[].mib` is measured for the in-process tracker
  (`memory_reserved`) and the cap for children.
- **motion.stats camera.** DIS flow at 320 px / 15 fps in a 16-column block grid; camera = robust translation + zoom
  fit on the textured border-ring blocks with the calmest 40 % flow variance. Verdict order: static (travel < 2 px and
  zoom < 1 %) → sway (the self-moving interior blocks turn with the camera, share ≥ 0.9) → rides (stroke-locked
  oscillation, half-cycle CV < 0.25) → move (2 s trend moving ≥ 3 s with ≥ 3 % net) → else sway. On the
  owner-approved trace-2 video: s0 sway 15 px [trace: static < 2 px; its border is flat paint plus bodies],
  s1 rides 37 px at 1.25 Hz CV 0.18 [34 px, 2.51 turns/s, CV 0.18], s2 move 40.4-55.2 s [push-in 40.5-50 s], s3 sway
  7 px [sway ~7 px]; still 81.8-84.4 s and 85.4 s-end [idle 80.4-84.8, credits from 84.8]. 10 s CPU for 104 s of
  1600x1400 45 fps (decode-bound). Phase correlation of border tiles was tried and dropped: on flat-painted animation
  the tiles have nothing to lock on.
- **motion.propose** is unproven (DESIGN §9): on the trace-2 clip's s1 its first axis sits at the penetrator clicks of trace 2,
  on s0 it picks the right edge, not the hip. 1-2 s per scene.
- **Measured** (`test_serve_vlm.py`, RTX 4090 shared with other jobs, gpu_lock 8 GB, Qwen3.5-2B bf16 via the VLM
  worker, 448 px, batch 8): serve hello 0.9-1.6 s (one-shot pays this per request); first `director.ask` 11-18 s
  (worker start + transformers import ~1.3 s + weights 5.8-7.9 s + warm-up); then 39-51 ms per single-frame
  question; peak reserved 4.7 GB (cap 6 GB). sam2_mask resident 1.0 GB reserved. Budget 8 GB: the VLM was evicted
  for sam2 (4.3) and sam2 + describe for the VLM again (reload 15 s). Bonsai was not run here (not cappable, 7.5-8.8 GB
  measured by the stage bench, over this job's 8 GB).

## Add a tracker (one file)

Create `pawtrack/trackers/my_tracker.py`. Files starting with `_` are not loaded.

```python
from pawtrack.registry import param, register

@register("my_tracker", "My tracker", roi="box", params=[   # roi: "box" | "points" | "none"
    param("strength", "Strength", "float", 0.5, 0.0, 1.0),
])
def track(frames, roi, p):
    import torch  # heavy deps imported HERE, never at module top: `list` must stay fast
    for t_ms, bgr in frames:          # full-res frames of one scene (cuts already split out)
        value = ...                   # float (any unit), (dx, dy) px displacement, or None if lost
        yield t_ms, value, {"points": [], "boxes": []}   # overlay, normalized 0..1 (+ optional "masks")
```

For several signals, pass `channels=[...]` to `register`, add a `primary` choice param, and yield a dict in place of `value`: `{"channels": {name: float|None}, "confidence": 0..1, "value": optional}`. Without `"value"`, the channel named by `p["primary"]` is the primary signal. A tracker that accepts a box or clicks declares `roi="box_or_points"`. See `trackers/sam2_mask.py`.

The core normalizes `value` per scene. A `(dx, dy)` value is projected onto its principal axis of motion. The core then runs the smoothing/points pipeline. If your tracker needs heavy deps, add an extra to `pyproject.toml`, for example `[project.optional-dependencies] my_tracker = ["torch>=2.5"]`, and install it once with `uv sync --project trackers --extra my_tracker`. Plain `uv run` does an inexact sync, so it keeps the extra. Add the deps and their licences to the table below. Check model weight licences too, and avoid AGPL (for example Ultralytics).
