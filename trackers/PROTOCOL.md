# pawtrack protocol (v3)

CoTracker3 (`cotracker_points`) is optional and not included (v4.57, below): it is in no build and its module is not in the public source. Wherever this file names `cotracker_points`, the shipped points tracker is `tapnext_points` with the same params and events.

Invoked as `uv run --project trackers pawtrack`. One request on stdin, JSON Lines events on stdout, then exit. Logs and tracebacks go to stderr only.
v2 is additive: every v1 request still works, and every v1 result field is still there with the same meaning. One v1 behaviour changed: `samples` now has an entry for every frame, with `null` where v1 left the frame out (see below).
v3 is additive over v2: new `score` command; optional `spans` and `activity` in `track`; new result fields (`track.scenes`, `loop.kind` / `prominence` / `motion_period_*`); new event kinds (`idle`, `carry`, `still`, `climax`, each with `end_ms`); new `pipe_*` params. Behaviour changes, all through param defaults (send the old value to get v2 output): `pipe_min_prominence` 0.15 -> 0.04, `pipe_rdp_epsilon` 15 -> 100 (extremes only), new `pipe_norm_window_ms` 3000 (v2 = 0), `pipe_gate` motion (v2 = off), `pipe_carry_gaps` true (v2 = false), `pipe_snap_frames` false (v2 = true). `loop.confidence` now measures exactness only (see loop). `describe` additionally runs a dense age check (see describe).
v3.1 (additive, no version bump in requests): span state and event kind `orgasm` = synthesized deep pulses (what a `climax` label produced in v3; same `pipe_climax_*` params). One behaviour change: a `climax` label now marks the fast run-in before the orgasm (the owner's "fast climax, then orgasm"): its points are kept as tracked and only the `climax` event is emitted. Send `orgasm` to get the v3 `climax` output.
v3.2 (additive): a track note may carry an optional `data` object (old clients ignore it); points trackers emit one note `primary` per scene (was `primary_used`, auto only) with the decision record (see notes).
v3.3 (additive): points trackers name their motion groups (bodies g1..g4, and parts g1p1.. where the result has them) from the shot tagger's heat maps: optional `scenes[].groups` and note `group_labels` (track param `group_labels`, default on). Not in the frame events.
v4.2 (additive, optional): `describe` takes `ranges` (several scenes, one process, one model load; see describe), sends progress stage `"model load"` while the tagger loads, and `serve` without a VRAM budget holds one GPU model kind at a time and unloads idle models (see `serve` specifics). Old requests and results are unchanged.
v4.3 (additive, optional): `track.roi.t_ms` = the media time (ms) the ROI was drawn on. The points trackers (`cotracker_points`, `tapnext_points`) seed the scene that contains it on that frame and track both ways from it (forward to the scene end, backward to its start); other scenes, and requests without it, seed per the new param `seed_frame` (`first` = the scene's first frame, the old behaviour and the default; `auto` = a frame picked from the scene's thumbnails). The `primary` note's data gains `seed` (see notes). Other trackers ignore `t_ms`. Old requests and results are unchanged.
v3.4 (additive): points trackers split each motion group into a body and up to 2 parts (a compact piece with its own motion on top of the body's: optional 5th `pts` element, channels `g{k}p{j}_*`) and add per-body `g{k}_scale` / `g{k}_rot`. The body channels now come from the body's rigid-motion inliers. Old clients ignore all of it.
v4.4 (additive, optional): `scenes` returns `camera` segments per scene (pawtrack/camera.py, CPU) and, with the new scene param `cut_camera` (default true), splits a scene where the camera turns progressive (pan / zoom / orbit / handheld) or steady again; the pieces after a scene's first carry `continues: true, split: "camera"` (the same shot, one continuing action: no cutaway, no bridge). `track` reports `scenes[].camera` and never splits a run at a camera move. Behaviour change in the points trackers' `pair_dist` / `pair_proj`: they follow a turning stroke axis (4 s windows) when the windows' axes span more than 20 deg over the run (a turntable); otherwise byte-identical. Old requests otherwise unchanged.
v4.5 (additive, optional): `scenes` resolves soft transitions in the same CPU pass (pawtrack/scenes.py): every scene carries `kind` ("blank" = a black / white stretch with its fades, "still" = a picture that does not change for >= 2 s: a title card, a frozen frame, or null) and `transition` {in, out: "cut" | "fade" | "dissolve" | null (the range's ends), in_ms?, out_ms?}. A fade to black now ends the scene where the fade starts (the blank, fades included, is its own scene), a dissolve gets one cut at its middle, a flash frame (content back within 80 ms) is no cut, and a still at a scene's start or end is split off. New scene params `cut_blank` (blank / fade / still, default true) and `cut_dissolve` (default true); both false = the v4.4 cuts except flashes and that a hard cut also keeps `cut_min_scene_ms` to the range's end. `track` without `cuts` runs the same detector over the range first (progress stage "scenes") and cuts at its scene starts. Old requests otherwise unchanged.
v4.6 (additive, optional): points trackers, box ROI: param `box_seed` gains `motion` (opt-in: more points where a cheap flow pass over the scene sees motion, a floor elsewhere; `grid` stays the default); new param `sem_groups` (default true): penis / balls / hips found by the shot tagger on the seed frame get a pinned share of the box's points that keeps its own group for the scene: channels `sem_<name>_*`, an optional 6th `pts` element, `scenes[].groups.sem_<name>`. The `primary` note's `seed` record gains `layout` / `flow_ms`. `primary: auto` picks `sem_hips_proj` on a box scene whose pinned hips are present on >= 50 % of its frames (rule "auto: pinned hips found on N % of frames → sem_hips_proj"; `primary_used` 2), and the note's `sem_*_proj` candidates carry `share` / `present`. Without the tagger (no `describe` weights or no CUDA) nothing changes; old clients ignore all of it.
v4.8 (additive, optional): pinned groups (`sem_groups`) are seeded on an outline of the CAM region (GrabCut by default) and pruned of members that do not move with their group; `scenes[].groups.sem_<name>` gains `source` "grabcut" | "sam" | "cam", `mask_px`, `blob_px`, `sam_reject`?, `pruned`, `tracked`?; the `primary` note's `seed` gains `shape_ms`, `track_ms`?; new channels `sem_<name>_area` (null unless the opt-in outline tracking runs), also valid primaries. Old clients ignore all of it.
v4.9 (additive, optional): `track.cuts` entries may be `{"t_ms", "kind": "hard" | "soft", "why"?}` (plain numbers stay hard). A **soft** cut (the action continues: a camera split, a `continues` scene, a camera move inside a scene) does not restart the tracker: one run goes through it with every live point, its index, group, part and pinned group; the points trackers run a re-seed pass there (see `cuts`) and the pipeline starts a new normalisation segment there (its own robust range, cross-faded, no step); a pinned group refilled there reports `scenes[].groups.sem_<name>.refilled` and the `reseed` note counts the soft-cut passes. New pipe param `pipe_cam_detrend` (default true): in a piece of the scene where the camera travels (the camera detector says pan / zoom / orbit / handheld, or the points trackers' camera path moves the primary by more than 1.5x the stroke) and the strokes are drowned (< half the piece's range) and periodic, the camera trend is removed from the primary before it is normalised (pipeline.cam_detrend). The record: `scenes[].segments` and the `primary` note's `segments`. `track` without `cuts` adds the `scenes` detector's camera splits as soft cuts. Behaviour change (send `pipe_cam_detrend: false` to get v4.8): primaries in camera-moving pieces. Hard cuts and old requests are otherwise unchanged.
v4.7 (additive, optional): new `cum` command: proposed cumshot (spurt) times over a range, from the describe tagger (spurt-tag probability and cum CAM mass rising) and new white fluid pixels near the penis, with optional contraction `pulses` from the caller; numbers only, nothing is placed (see cum). In `serve` it runs in the describe child. Old requests and results are unchanged.
v4.10 (additive, optional): a PARAM may carry `hint` (str): the explanation behind a short `label`, for a tooltip. Labels were shortened; keys, types, defaults, bounds and choices are unchanged.
v4.11 (additive, optional): the owner's own groups. New command `suggest_groups` (see below): the regions the points trackers would pin on a frame, as polygons, for the owner to refine. `track` takes optional `groups` (see below): in the scenes they belong to they REPLACE the tagger's pinned groups (`sem_groups`); a pinned user group is seeded, kept out of the motion clustering, pruned and re-seeded inside its own hull exactly like a v4.6 pinned group, under ANY name: channels `sem_<name>_x/_y/_n/_proj/_rel/_scale/_area` (also in `result.channels`, beyond the tracker's `channels` list), `scenes[].groups.sem_<name>` with `source` "user" and `id`. The pts 6th element is the group's id: penis / balls / hips keep 1 / 2 / 3, any other name gets 4, 5, ... in request order. A group named hips keeps the `primary: auto` hips rule. Without `groups`, and in scenes without one, nothing changes.
v4.12 (additive, optional): two characters. A `track.groups` entry may carry `who` ("c1" | "c2"), `part` and `side` ("l" | "r"); with a who or a part the name is derived as who_part_side ("c1_penis", "c2_hand_l"; underscores kept, so channels are `sem_c1_penis_*`), and a pinned user group then gets id 4, 5, ... like any other name. New channels per character with pinned groups: `who_c1_x/_y/_n/_proj` (`who_c2_*`): the seed-anchored centre of all its groups' members; and between them, on the stroke axis: `who_pair_dist/_proj` (C1 centre to C2 centre), `who_p1h2_*` (C1's penis to C2's hips), `who_p2h1_*` (C2's penis to C1's hips), each where both ends exist; their `_proj` are `primary` note candidates (reporting only: `primary: auto` never picks them). The hips rule of `primary: auto` follows the first group whose part is hips (a plain hips group first, else c1_hips / c2_hips in request order). Pinned points per group: 10 % of box_points (>= 6) scaled down evenly so all groups together stay at most half the box (`sem_budget`; 1024 points: 16 groups get 32 each). `suggest_groups` adds sheath and slit (genital_slit / cloaca) and returns `who`, `part`, `side` per group with `name` = who_part_side (behaviour change: v4.11 names were the bare part). Groups without who / part, and old requests, are unchanged.
v4.13 (additive, optional): the previous shot's groups as a clue. `suggest_groups` takes `prior`: [{name, who?, part?, side?, poly?}] (the groups of the shot before a hard cut inside one scene of the app: the same parts, at new places). The suggestions that re-find a prior identity take it (name, who, part, side; C1 / C2 of the suggestions are swapped first when the characters changed sides at the cut; per part the nearest to the prior polygon's centre) and carry `"prior": <its name>, "unconfirmed": true` (the owner accepts or repaints); the result gains `missing`: the prior names with no suggestion of their part (pawtrack/partlabel.match_prior). Without `prior` nothing changes. The app sends the re-found groups as ordinary `track.groups` (same names, so the channels `sem_<name>_*` continue across the cut).
v4.14 (additive, optional): parts-first tracking (owner, 2026-11-09: a sparse grid plus well-seeded groups tracks best). Points trackers, box ROI: new param `group_points` (default 0 = the v4.12 share of the box): every group (pinned, a `body` seed hull, or the tagger's) gets exactly that many points of its own ON TOP of the box's `box_points`, so the grid becomes the independent background count and a run seeds `box_points + groups x group_points` points (TAPNext++'s VRAM cap counts them; `cotracker_points.group_total`). New param `group_seed` ("spread" default = the v4.8 placement on textured pixels 1 px inside the outline; "corners"): a group's points go on the strongest corners (Shi-Tomasi) of the seed frame (at its own width, <= 640 px) at least 0.2 x the region's equivalent radius inside its outline (or the frame edge), spread by farthest-point sampling; deterministic (`cotracker_points.pick_corners`). New param `group_fit` (default false): a pinned group's motion comes from a robust similarity fit (`groups.rigid_fit`: IRLS, Tukey-weighted, each point weighted by the tracker's confidence) from its members' reference positions (the frame with most of them visible; a member first seen later learns its own from the fit) to the visible members, so outliers (a point slid onto the background) are down-weighted and a member dropping out does not move the centre: `sem_<name>_x/_y` (and so `_proj`) are the fit's centre, and new channels `sem_<name>_size` (scale vs the reference frame, 1 = same), `sem_<name>_rot` (radians, > 0 = clockwise on screen) and `sem_<name>_fit` (inlier share of the visible members' weight, 0..1: low = the group is unreliable there); a pinned point lost longer than retire_ms (or pruned) is re-seeded where the fit puts its own reference (in frame), else inside the hull as before. Old requests are unchanged. Not done: forward/backward consistency (it needs a second full tracking pass per scene, about 2x the runtime).
v4.15 (additive, optional): track direction (owner: track backwards from the start of a shot, e.g. a pan that arrives at the action). `track` takes `direction` ("both" default = as before | "forward" | "backward") and `seed_ms` (the seed frame; default `roi.t_ms`). forward = [seed_ms, end_ms), backward = [start_ms, seed_ms] (seed frame included): `start_ms` / `end_ms` stay the outer limits (the app sends the previous / next hard cut or the owner's range), the run never crosses the seed, `roi.t_ms` becomes `seed_ms`. backward needs a points tracker (`seed_frame` param: they track the buffered scene backwards from the seed; others are refused). Output times run forward as always (the reversed pass is mirrored). A one-way points run stops where its points are lost: walking from the seed in the direction, the first span of >= 500 ms where under 25 % of the tracked points (the pinned groups' when there are any, else the original seed points) are visible ends it there (`cotracker_points.lost_stop`; a `lost` note {t_ms, dropped}); the frames beyond are not emitted. The app sends the cuts it tracks through as soft (one run through them, a normalisation boundary). Old requests are unchanged.
v4.16 (additive, optional): spurts from contractions (owner: "anus contraction with sam to track spurts too"). `cum` takes `groups` (the scene's painted groups, track.groups' shape plus optional `pulse`: bool) and `pulse_range` [a, b] (ms: the orgasm span). The pulse groups (`pulse` true, else part / name ending in `anus`) are tracked over pulse_range (clipped to the request's range) +- 1 s (the margin may reach past it; SAM never runs on the whole video; their events outside the request's range are dropped) by pawtrack/pulse.py: SAM 2.1 masks on a crop around the region (seeded from the polygon: box + points inside, negatives at the other groups on its frame), the CPU points fallback (dense radial flow in the region against the body ring around it) when SAM is off (`pulse_sam` false), missing or fails. Each contraction is a cue that `merge` joins with the visual peaks: every spurt gains `why` [{cue, score?}] (cue = "anus (C2)", "tag", "cam", "fluid", "balls pulse"), the score of agreeing cues is 1 - prod(1 - s), a shot's time is its contraction's (the drawing where it appears). The result gains `pulse` (per group: name, label, source sam | points, events [{t_ms, score, z, weak}], range, frames, sign, sam_ms?, lost?, crop?, note?) and `channels` {"sem_<name>_pulse": [[t_ms, v | null], ...]} (sigma units, > 0 = contracted). New params: cue_ms 200, pulse_sam true, pulse_model small, pulse_offset_ms 0, pulse_sign auto. Progress stage "pulse" while it tracks. `suggest_groups` adds anus (anus / presenting_anus / puffy_anus / spread_anus / gaping_anus). Without `groups` nothing changes except `why` on each spurt.
v4.17 (additive, optional): shaft consumption (owner: "a shaft consumption sam tracker on TOP of seeded grid tracking, so we have an accurate amount of the penis that is inside"). A `track.groups` entry may carry `shaft: true` (a pinned penis group, points trackers). After the points tracker has tracked a scene, pawtrack/shaft.py measures how much of that shaft is inside: SAM 2.1 masks of the visible shaft on a crop that follows the group, re-prompted from the group's tracked members (a fresh box + positives from the visible members, negatives at the other groups' members) every `shaft_reprompt` frames (default 48) and whenever the mask drifts off the members; the axis and the base point come from the members' similarity fit (base end: nearest the same character's balls / sheath / hips, else away from the partner); the visible length L runs from that base point to the entry edge (the far end of the mask), over the shaft's own width (zoom cancels); the full length is the 90th percentile on frames whose tip is free of the partner's receiving groups (anus / slit / hips / head / torso / body), else the largest seen (`full: "relative"`). New channels per shaft group (also in `result.channels`): `sem_<name>_in` (inserted fraction 0..1, 1 = all in; null where unknown, e.g. a hand at the entry edge), `_in_conf` (0..1: SAM's confidence x no holes along the axis x off the crop edge x base end in place x not foreshortened (the members' scale along the axis against the mask width) x 0 where a hand / paw / tail and not the partner sits at the entry edge; a free tip shorter than 0.8 x full = foreshortened, x 0.3), `_len` (visible length / full length, larger = out), `_knot` (scene tagged knotting and a bulge >= 1.3 x the width seen in the base 70 %: 0 out, 0.5 at the entrance, 1 in; null otherwise), `_bx` / `_by` (base point) and `_ex` / `_ey` (entry edge), normalized frame coordinates, `_w` (shaft width, frame heights). Knot state changes held >= 2 frames are `events` {kind "knot", dir "in" | "out", label "knot in (<name>)", source "shaft"}. `scenes[].shaft` = {<name>: {source "sam" | "points" | "none", base_from "own" | "partner" | "hidden", frames, members, full "seen" | "relative", l_full_w (full length in widths), conf_share, knot? {at_w, half_w}, sam_s?, video_s?, sam_s_per_s?, chunks?, drift?, lost?, note?}}. Direction: where the most confident shaft group's visible length correlates with the scene's primary (|r| >= 0.3 over >= 50 % confident frames), it sets the scene's `sign` (behaviour change for scenes with a shaft group: over `pipe_sign` keep / auto; `pipe_invert` still applies); the `primary` note's `sign` gains `shaft` {sign, r, share, confident} and `mode` "shaft". Without SAM (`shaft_sam` false, sam2 missing, a failure) the channels come from the members alone (`source` "points": the farthest visible member's place along the shaft; coarse; `full` "relative"; no knot; it never sets the direction: on the owner's runs the tracker keeps the members "visible" while they slide over the partner). New params (not listed by `list`, accepted by `track`): shaft_sam true, shaft_model small, shaft_reprompt 48, shaft_stride 1 (SAM on every Nth frame, interpolated). Progress stage "shaft". Groups without `shaft`, and old requests, are unchanged.
v4.18 (additive, optional): the learned seeder (paw-bn2, paw-pqi; measured in experiments/seeder-probe). New command `seed_train` (see below): a small part head (pawtrack/seeder.py: 1152 -> 256 -> 9 parts MLP on the Hydra tagger's own 16 px patch features, the probe's recipe: 10 epochs, heat >= 0.5 blobs, no GrabCut / SAM) trained on the painted groups (source "user" or none) of the `.pawproj` files in the given folders plus projects, stored under `dir` with a feature cache per frame. `suggest_groups` takes `seed` {dir, key?}: the parts the head has >= 5 painted examples of from >= 2 videos come from its heat (groups with `source` "seeder", `outline` "head", `score` = the blob's peak heat, `tentative: true` below 0.7); the others keep the tag CAM as before; key (the video's media hash) names C1 / C2 after that video's painted characters (each group of a two-character split gets `named` "painted" | "left"); the result gains `seeder` {frames, videos, trained_at, parts} (null: none trained yet). `suggest_groups` with `t_ms` takes `candidates` [ms] (frames of the shot's first 2 s): each is scored by the parts it shows confidently (head peak >= 0.7, else the tags at CONF) and the suggestion is made on the best (ties: the first listed), `frame` "best", result `candidates` [{t_ms, parts}]. Behaviour change (param `who_split`: "position" gets v4.17): without SAM bodies, a two-character frame (2-means says so, or a non-paired part appears twice) is split by appearance + position with every non-paired part at most once per character (probe: 0.84 vs 0.68 grouping on painted parts); one character stays one. Without `seed` / `candidates` the parts come from the tag CAM exactly as in v4.17.
v4.19 (behaviour change, param to undo): naming Bottom / Top (c1 / c2; paw-cq4). `suggest_groups` param `who_left` ("head" default | "parts" = v4.18): when the video has no painted scene to name the characters from (no `seed.key` match), C1 is the character whose **head** is further left (the mean of its parts' centres when it has no head), no longer the one whose parts' mean centre is further left: in contact both characters' hips / penis sit at one place and a stray part pulls the mean, the heads stay apart (verify_seeder.py leave-one-video-out, absolute C1/C2 on the CPU tagger 0.56 -> 0.69, on the GPU tagger as the app runs it 0.63 -> 0.70; the split itself is unchanged). Applies to every two-character suggestion (SAM bodies too); send `who_left: "parts"` to get v4.18. Nothing else changes.
v4.20 (additive, optional): seed-frame weights (paw-8yip). `suggest_groups` with `candidates` takes `candidate_bonus` [float], one per candidate (same order): added to a candidate's parts count when the best frame is picked (ties: the first listed; `cli.pick_candidate`). The app weighs frames that repeat exactly elsewhere in the video (min(1.5, 0.5 log2 repeats)) and the owner's chosen loop frame (+2), so the parts count stays the main criterion. Result `candidates` entries gain `bonus` where one was sent. Without `candidate_bonus` nothing changes.
v4.21 (additive, optional): seed points per group (paw-8mf4). A pinned `track.groups` entry may carry `points` [[x, y], ...] (>= 1, 0..1 frame, clipped): the points trackers seed that group on exactly these points on its frame (`cotracker_points.box_seeds` `fixed`; the group's share of `box_points`, or `group_points`, is replaced by their count; not clipped to the box) instead of laying them inside `poly`, which stays required (its outline still serves the opt-in outline tracking, the pulse / shaft passes and older sidecars, which ignore `points` and seed inside it). The app sends them for a take filled from a stored run's seeded points on an exact repeat of a tracked frame. Groups without `points` are unchanged.
v4.22 (behaviour change, no new fields): every tracker runs both ways from its seed frame (paw-2nul; owner: "any and all trackers should work forwards and backwards, just play the video in reverse"). Before, the points trackers (`cotracker_points`, `tapnext_points`) already seeded the scene holding `roi.t_ms` (or a group's `t_ms`) there and tracked the buffered scene both ways; `lk_box`, `lk_two_point`, `template` and `sam2_mask` ignored `roi.t_ms` and applied the ROI to each scene's first frame, and `direction: "backward"` was refused for them. Now, in the scene holding `roi.t_ms` (past its first frame), those trackers run backward from the seed frame (the last frame at or before `roi.t_ms`) to the scene's first frame on the video played in reverse (`cli.reverse_frames`: re-decoded 32 frames at a time, the same frames as forward), then forward from it on the stream (`cli.both_ways`); the halves run one after the other (a pass's state is gone before the next), the seed frame's row is the same in both (the forward one is kept), and the rows are one run in time order: samples, frame events, overlays and the pipeline see an ordinary scene (cadence fill, loop fold and normalisation run on the stitched scene). Progress stage `tracking backward` during the reversed half. `direction: "backward"` works for every tracker. Scenes seeded on their first frame (no `roi.t_ms`, or it falls in the first frame, or in another scene) are unchanged, bit for bit.
v4.23 (behaviour change, param to undo): auto levels for the frames the trackers see (paw-p63x; owner: "feed it normalized data, not a small section"). New track param `input_levels` ("auto" default | "off" = the frames as decoded = v4.22), listed with every tracker's params. Per scene (a span between hard cuts; soft cuts do not split it) one photometric adjustment is computed once from <= 24 frames spread over the scene plus the seed frame (pawtrack/levels.py, a separate decode at 320 px) and applied identically to every frame the tracker gets, both halves of a both-ways run alike (cli: one wrapper in the scene's frame iterator, one on `reverse_frames`): luma black / white points at p1 / p99.5 of the sample (letterbox bars and pure-black frames ignored; 40 / 30 levels of margin, so well-exposed footage stays put) stretched linearly with gain <= 4, then a gamma in 0.5..2 that moves the median into 0.30..0.55 (never lifting a midtone by more than 4x), one LUT on all channels; HSV saturation x k <= 2 so the median saturation reaches 0.20 (skipped for near-greyscale footage and when already >= 0.15); a result within 10 levels of the identity is dropped. Coordinates, overlays, scene detection, thumbnails and the other passes (repeats, describe, suggest_groups, seeder) are untouched. Result: `scenes[].input` = {mode: "auto" | "off", applied, why? ("unchanged" | "flat sample" | "no usable frames"), black, white, gain, gamma, saturation, lift (median output / input), capped: ["gain" | "gamma" | "saturation" | "noise gain"], frames, p1, median, p99_5}. Note: the points trackers' own tagger passes (pinned groups, group names) run on the adjusted frames.
v4.24 (additive, optional): image labels for the learned seeder, and five new parts (paw-714j). `seed_train` takes `labels` (a folder path): the app's still-image labels, one JSON per labelled image, `<key>.json` = {image (absolute path), key, w, h, groups: [the .pawproj group encoding: name, who, part, side, poly, mask {w, h, rle}, source "user"], none?: true, savedAt} (`seeder.image_labels`). Each labelled image is ONE frame of its own source (its key; t 0), so it counts as its own "video" for the >= 2 sources rule; its features come from the image file through the same cache (`feats/<key>_0.npz`, tagger on CUDA for images not seen yet; a missing or undecodable image is skipped and counted) and its targets from the painted masks exactly as a project frame's; `none: true` ("nothing to label here") is a frame with no parts, every patch a negative (the training loop needs no change); an image whose groups are all unusable (unassigned, body, other) is skipped. The fingerprint that makes a repeat `seed_train` a no-op now includes the image labels and the part list. Result gains `images` (image frames used), `negatives` (of them without parts) and `projects.labels` ({frames, groups, skipped: {none, missing, broken, no_parts, ...}}). New parts, in the app's groups.js PARTS and the head's classes (ids carry no underscore: a group name is who_part_side): `knot`, `thighs` (paired l / r like hand and paws), `tongue`, `stomachbulge`, `neckbulge`. ## Shared track params

Every tracker accepts its own params plus these groups (all listed in each tracker's `params`):

- `pipe_*`: smoothing / points pipeline.
- `cut_*`: cut detection. `track` splits the range at cuts, re-seeds the tracker from the ROI and normalizes each scene on its own. `cut_blank` / `cut_dissolve` (v4.5, default true): blank, fade and still segments / a cut at each dissolve (pawtrack/scenes.py has the thresholds); `cut_min_scene_ms` applies to hard cuts only.
- `held_retime` (`off` | `auto` | `on`, default `auto`): for animation on twos/threes, keep one sample per distinct drawing, at the frame where it appears, and interpolate linearly in between, so there are no staircases. `auto` applies it when the dominant held step is >= 2.
- `loop_fold` (`off` | `auto` | `on`, default `off`): if the scene loops exactly (same frames every N frames), take the median of every phase over all cycles and tile it back. Every cycle is then identical and lost frames are filled in. A `cycle` event is added at each cycle start (the scene's first frame is phase 0). `auto` needs `confidence >= loop_min_confidence`. `on` folds whenever a period is found. Both need at least 2 cycles in the scene.
- `loop_min_confidence` (0..1, default 0.5): also the only `loop_params`. With v3's exactness confidence, `auto` folds exact loops only; periodic motion is never folded by `auto` (on the reference set folding periodic motion lost F1: its cycles differ in depth and timing).

## GPU memory

Every GPU part caps the process's CUDA allocations (`torch.cuda.set_per_process_memory_fraction`) so nothing spills into system memory, through one place (`pawtrack/vram.py`, paw-szyg): the models a process keeps loaded between jobs are a registry (name, size measured on load), and the cap is (every resident the job does not use) + (the job's own needs: its tracker's measured need, plus the tagger's 1.8 GB / SAM's 0.6 GB when it uses them; describe 3 GB, sam2_mask max(3, 2 + 0.004 x chunk_frames) GB). When that exceeds the budget, the residents the job does not use are unloaded first, least recently used first. Budget: env `PAWSCRIPT_GPU_FRACTION` (set by `trackers/gpu_lock.py`) x the card, else env `PAWTRACK_VRAM_GB`, else the card's free memory plus what the process holds, less 1 GB; with either env var the cap is that budget itself. On a CUDA out-of-memory error anyway, the job's unused residents are unloaded and the job runs once more (only when it has not streamed `frame` / `described` events yet); a second one ends in an error event that says in words what was loaded and what the job needed (no raw PyTorch message). `unload` / log names of in-process models are the registry's (`tapnext_points:512`, `hydra`, `sam_image`, ...).

## Tracker channels and units

`sam2_mask` (roi `box_or_points`: a box, or positive clicks), channels measured on the mask:

| channel | unit |
|---|---|
| `centroid_x`, `centroid_y` | normalized frame coords (0..1, y down) |
| `area` | fraction of the frame area |
| `axis_len` | length along the principal axis, in frame heights. It is the long side of the rectangle with the same second moments |
| `axis_width` | the short side of that rectangle, in frame heights |
| `len_over_width` | `axis_len / axis_width`, unitless. This is the scale-free visible length, the insertion-depth candidate |
| `axis_angle` | degrees, screen counter-clockwise from horizontal, in [-90, 90) (wraps at ±90) |
| `bulge` | max slice width in the basal third of the axis / shaft width (25th percentile of the slice widths), unitless (≈1 for a plain rod). `null` if undefined |
| `raw_px` | the primary in frame px before normalization: centroid coordinate (y: up = higher) for `centroid_x` / `centroid_y`, distance from the first centroid for `centroid_auto`, else `axis_len` in px |

Param `primary` picks what becomes `samples`/`points`: any channel, or `centroid_auto` (centroid projected on its principal axis of motion, like `lk_box` `axis:auto`). Default `len_over_width` (shorter visible length = deeper = lower pos). As a primary, `centroid_y` is flipped so that image-up = higher value, like the other trackers (geometry only, not depth). `confidence` is the sigmoid of SAM 2's object-presence score.

Timestamps must come from the container's presentation timestamps (handle VFR), never frame_index/fps.
